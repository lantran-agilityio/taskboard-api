# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

A practice project for learning how to work with AI to reverse engineer a product: observe Trello's public behaviour, turn it into requirements, design a UI prototype, and write a build plan (see "Reverse-engineering workflow" below and `docs/`). The finished Trello-style task board API (`taskboard-api`, roadmap steps 1–11) is the backend those plans build on, and the answer key the build plan is checked against. Verify the API through tests and the Swagger UI at `/docs`. The real UI is in `frontend/` (roadmap steps 22–28, `docs/build-plan.md`); steps 29–32 (in the build plan's "After the build order") check it, test it with two people, observe again and extend it. The clickable prototype in `prototype/` stays its design reference.

Domain: a **user** owns **boards**; a board has ordered **lists** and its own **labels**; lists and cards can be **archived** (hidden, kept, restorable) as well as deleted; a list has ordered **cards**, each with an optional due date (and done flag), labels from its board, assignees (the board's owner or members), and ordered **checklists** of ordered items that can be ticked. Cards can move between lists of the same board, and their order must stay consistent after every move. Users register and log in for a JWT; every board, list and card endpoint needs it. The board's creator is its owner and can share it with other users as **editor** or **viewer**:

| Action | Viewer | Editor | Owner |
|---|---|---|---|
| Read the board, lists, cards, labels, members; search cards | ✓ | ✓ | ✓ |
| Create/rename/move/sort/delete lists and cards | 403 | ✓ | ✓ |
| Set card details; add/change/delete checklists and their items; create/change/delete labels | 403 | ✓ | ✓ |
| Archive/restore lists and cards | 403 | ✓ | ✓ |
| Read comments and the activity log | ✓ | ✓ | ✓ |
| Comment on cards; edit or delete your own comments | 403 | ✓ | ✓ |
| Delete others' comments | 403 | 403 | ✓ |
| Star or unstar the board (for yourself) | ✓ | ✓ | ✓ |
| Change the board's description | 403 | ✓ | ✓ |
| Rename/delete the board, close/reopen it, add members, change roles, remove others | 403 | 403 | ✓ |
| Leave the board (remove yourself) | ✓ | ✓ | 422 |

Users who aren't on a board get 404 for it and everything in it. A **closed** board is read-only for everyone: every write on it is a 422 (after the role check), except reopening, deleting, leaving and starring. Cards have **comments**, and every board has an **activity log** of everything that changed on it; both are paginated with a cursor, newest first.

- `app/main.py` — the FastAPI app; registers routers, and its `lifespan` starts and stops the realtime listener. It doesn't create tables: Alembic migrations own the schema.
- `app/core/config.py` — `Settings` (pydantic-settings, reads `.env`); `DATABASE_URL` defaults to local PostgreSQL database `taskboard`, `TEST_DATABASE_URL` to `taskboard_test` (psycopg 3, `postgresql+psycopg://`). `SECRET_KEY` (signs JWTs) has no default, so the app won't start without it: copy `.env.example` to `.env`.
- `app/core/security.py` — password hashing (pwdlib, Argon2) and JWT create/decode (PyJWT, HS256, `sub` = user id). Plain functions, no FastAPI.
- `app/core/database.py` — `make_engine()` (with `pool_pre_ping`, so pooled connections killed by a database restart are replaced instead of failing a request; the tests' `engine` fixture uses it too), engine, `SessionLocal`, the declarative `Base` (with a constraint naming convention, so migrations can refer to constraints by name, and `datetime` mapped to `timestamptz`), and the `get_db()` dependency.
- `alembic/` — migrations. `env.py` takes the URL from the Alembic config if set (the tests do) or else `settings.database_url`, and imports `app.models` so every table is known. New revisions are formatted by ruff (hooks in `alembic.ini`).
- `app/models/` — SQLAlchemy models, one file per model: `User` (`user.py`, unique lowercased `email`), `Board` (`board.py`, `owner_id` → users, optional `description`, `closed_at` while closed), `BoardMember` (`board_member.py`, composite key `(board_id, user_id)`, `role` is a `BoardRole`; the owner is never a member row, only `Board.owner_id`), `BoardList` (`board_list.py`, table `lists`; not named `List` to avoid confusion with Python's `list`), `Card` (`card.py`; `due_at`, `due_complete`, and `labels`/`assignees` with read-only `label_ids`/`assignee_ids` properties for `CardRead`, plus `board_id` (through its list, which is loaded wherever cards are read, so it costs no query: a link to `#card-<id>` can find its board); `comment_count`, `checklist_done` and `checklist_total` are `column_property`s (correlated `COUNT` subqueries), so they load in the same `SELECT` as the card) and `Label` (`label.py`; `color` is a `LabelColor` stored as Postgres enum `label_color`; `name` may be empty (`LabelName` in `app/schemas/label.py`, not the shared `Name`); `Board.labels` cascades deletes; `create_board` gives every new board six unnamed labels, one per colour in enum order, without publishing label events, and logs one `board.created` event, so a board's history starts with its creation). `card_details.py` holds the plain association tables `card_labels` and `card_assignees` (many-to-many, `ondelete=CASCADE`). `board_star.py` holds the plain table `board_stars` (`(user_id, board_id)` key, no relationship on `Board`; the database cascade removes a deleted board's stars). `Board.lists` and `BoardList.cards` are ordered by position and cascade deletes, so deleting a board deletes its lists and their cards (and `User.boards` cascades the same way) (the foreign keys also have `ondelete="CASCADE"` for databases that enforce it). `app/models/__init__.py` imports every model so relationships can find each other by name; add new models there. `lists` has `UNIQUE (board_id, position)` and `cards` has `UNIQUE (list_id, position)`, both `DEFERRABLE INITIALLY DEFERRED`: checked at commit, so renumbering may pass through duplicates mid-move. Lists and cards have `archived_at`, and `archived_position` (where it was, so restore puts it back there, clamped to the end; `NULL` for items archived before migration 0007, which restore at the end); an archived item has `position = NULL` (unique constraints ignore NULLs), enforced by the CHECK constraint `position_iff_active`. `Board.lists` and `BoardList.cards` hold every item, archived or not (so deletes cascade); `Board.active_lists`/`archived_lists` and `BoardList.active_cards`/`archived_cards` (helpers in `app/models/archive.py`) give the active ones in position order and the archived ones newest first. `Card.is_frozen`: the card or its list is archived. `Checklist` (`checklist.py`, `card_id`, `title`, `position`; `Card.checklists` ordered by position) and `ChecklistItem` (`checklist_item.py`, `checklist_id`, `text` (1–500), `done`, `position`; `Checklist.items`): both have `UNIQUE (parent_id, position)` `DEFERRABLE INITIALLY DEFERRED`, no archiving (positions never `NULL`), and `passive_deletes`, so the database cascade deletes them with their card. `Comment` (`comment.py`; `Card.comments` with `passive_deletes`, so the database's cascade deletes them) and `Activity` (`activity.py`, table `activities`: `board_id`, `actor_id`, `type` (an `EventType` value), `data` (JSONB), with index `(board_id, id)`; no relationship on `Board`, the database cascade deletes a board's log).
- `app/schemas/` — Pydantic request/response schemas, one file per model. `common.py` holds `Name` (trimmed, 1–100 characters), shared by boards, lists and card titles, and `Description` (0–2000 characters), shared by boards and cards. In `CardUpdate` and `BoardUpdate`, `description: null` clears the description, and leaving it out keeps it (checked with `model_fields_set`). `BoardRead.starred` and `BoardRead.role` are per caller and `list_count`/`card_count` (active lists, and active cards in active lists) come from other tables, so routes build it with `board_read()`/`read_board()` in `app/api/routes/boards.py`, and `board.*` events leave all four out (`PER_CALLER`).
- `app/services/permissions.py` — `board_role(board, user_id)` (owner, member role or `None`) and `allows(role, minimum)` (viewer < editor < owner). The only place that decides who may do what.
- `app/services/card_details.py` — `resolve_labels()` and `resolve_assignees()` (the ids must be on the card's board, else `ValueError`, which routes turn into a 422 on `label_ids`/`assignee_ids`) and `unassign_from_board()` (called when someone leaves a board).
- `app/services/stars.py` — `star()` (`INSERT … ON CONFLICT DO NOTHING`, so repeats and races are harmless), `unstar()`, `starred_ids()` (one query for `GET /boards`) and `is_starred()`. Also called when a member leaves a board. Stars publish no events: they're per user.
- `app/services/board_counts.py` — `board_counts(db, board_ids)`: active lists and their active cards per board, in one grouped query (boards with no lists are missing: read them as (0, 0)). `GET /boards` uses it with `starred_ids()` and `selectinload(Board.members)`, so its query count doesn't grow with the number of boards.
- `app/services/activity.py` — `card_id_of(Activity.data)`: the SQL expression for the card an activity entry is about (`data.card.id`, `data.card_id` or `data.comment.card_id`, else `NULL`), for the activity log's `card_id` filter.
- `app/services/pagination.py` — `paginate(db, query, id_column, limit, before)`: keyset pagination, newest first (`id < before`, fetches `limit + 1` to know whether there's another page); returns a `PageResult` that `Page[T]` (`app/schemas/page.py`) is built from.
- `app/services/ordering.py` — `remove_item()` (takes an item out and renumbers the rest; used by delete and archive), `move_item()`, `transfer_item()` (moves an item from one sequence into another, such as a card between lists), `insert_item()` (puts a restored item back at a position, clamped to the end), `sort_items()` (renumbers by a key, for `POST /lists/{id}/sort`) and `renumber()`: keep `position` values of a board's lists and a list's cards at 0..n-1. Plain Python, no FastAPI or database code.
- `app/api/access.py` — dependency factories `board_access(min_role)`, `list_access()`, `card_access()` that load the item and check the role on its board (404 if none, 403 if too low), `label_access()`, plus the aliases `ViewableBoard`, `EditableBoard`, `OwnedBoard`, `ViewableList`, `EditableList`, `ViewableCard`, `EditableCard`, `ViewableLabel`, `EditableLabel`, `comment_access()` with `ViewableComment` and `EditableComment`, and `checklist_access()`/`checklist_item_access()` with `ViewableChecklist`, `EditableChecklist` and `EditableChecklistItem`. Write access (editor or owner) also locks the board row (`SELECT … FOR UPDATE`) before loading the list or card, so concurrent reorders of one board take turns; one lock per request, so no deadlocks. Write access to a closed board is a 422 (`Board is closed`, on `board_id`) in `load_board()`, so every `Editable…`/`OwnedBoard` route gets it for free; `OwnedBoardAnyState` skips it, for close, reopen and delete. `remove_member` (a `ViewableBoard` route) checks it itself, letting people leave.
- `app/api/deps.py` — `get_current_user()` (reads the bearer token via `OAuth2PasswordBearer`, 401 if missing, invalid, expired or the user is gone) and the `CurrentUser` alias; `Pagination` (the `limit` (1–100, default 20) and `before` query parameters).
- `app/api/routes/` — one file per resource; register its routers in `app/main.py`. `auth.py`: `POST /auth/register`, `POST /auth/token` (OAuth2 password form; `username` holds the email) and `GET /users/me`. `boards.py`: `POST`/`GET /boards`, `GET`/`PATCH`/`DELETE /boards/{board_id}` (`PATCH` takes `EditableBoard`, and a `name` change also needs the owner, else 403) and `PUT`/`DELETE /boards/{board_id}/star` (viewers and up, 204), `POST /boards/{board_id}/close` and `/reopen` (owner, events `board.closed`/`board.reopened`), and `GET /boards/{board_id}/snapshot` (viewers and up: `BoardSnapshot`, the board with its active lists and their active cards in board order, eager-loaded with `selectinload` so the query count doesn't grow with the board; labels and members stay separate). `GET /boards` shows open boards, or with `?closed=true` the closed ones, most recently closed first. `members.py`: `GET`/`POST /boards/{board_id}/members` and `PATCH`/`DELETE /boards/{board_id}/members/{user_id}` (the owner is listed first with role `owner`, but can't be changed or removed). `lists.py` has two routers: `board_lists_router` (`POST`/`GET /boards/{board_id}/lists`) and `router` (`GET`/`PATCH`/`DELETE /lists/{list_id}`; `PATCH` renames and/or moves; `POST /lists/{list_id}/archive` and `/restore`; `POST /lists/{list_id}/sort` with `by` (`SortBy` in `app/schemas/board_list.py`), which returns the cards and publishes one `list.sorted` event). The list `GET`s take `?archived=true` for archived items, newest first. `cards.py` follows the same pattern: `list_cards_router` (`/lists/{list_id}/cards`) and `router` (`/cards/{card_id}`); its `PATCH` can also move a card to another list on the same board (`list_id`, which defaults to the end of the target list) and set the details (`label_ids`/`assignee_ids` replace the whole set; `due_at: null` clears it), and is a 422 for a frozen card; `POST /cards/{card_id}/archive` and `/restore`; `board_cards_router` is `GET /boards/{board_id}/cards`, the board-wide search (`label_id`, `assignee_id`, `due_before`, in board order). `labels.py`: `board_labels_router` (`POST`/`GET /boards/{board_id}/labels`) and `router` (`GET`/`PATCH`/`DELETE /labels/{label_id}`). `comments.py`: `card_comments_router` (`POST`/`GET /cards/{card_id}/comments`; 422 to write on a frozen card) and `router` (`GET /comments/{comment_id}` for viewers and up, so a link can open one comment's card; `PATCH`, author only; `DELETE`, author or board owner, also on frozen cards; others get 403). `checklists.py`: `card_checklists_router` (`POST`/`GET /cards/{card_id}/checklists`; `title` defaults to `Checklist`; `GET` returns each checklist with its items), `router` (`GET`/`PATCH`/`DELETE /checklists/{checklist_id}`, `PATCH` renames and/or moves within the card; `POST /checklists/{checklist_id}/items`) and `items_router` (`PATCH`/`DELETE /checklist-items/{item_id}`: `text`, `done`, `position` within its checklist); every write is a 422 on a frozen card; events `checklist.*` and `checklist_item.*` carry a top-level `card_id`, so the activity log's `card_id` filter finds them. Hiding ticked items is client-side. `activity.py`: `GET /boards/{board_id}/activity`, with `kind=comments` (only `comment.*` entries) and `card_id=` (one card's entries, through `card_id_of()`; not checked against existing cards, so a deleted card's history stays readable). Both `GET`s return `Page[...]`.
- `app/realtime/` — board events over WebSocket. `events.py`: `EventType`, `publish(db, board_id, type, data, actor_id=...)` (adds an `Activity` row (except for `board.deleted`) and sends a Postgres `NOTIFY` on channel `board_events` with `actor_id` in the payload; both happen only if the transaction commits), and `list_order()` / `card_order()` for the new orders events carry. `hub.py`: `BoardHub` (`hub`), this process's sockets per board; `dispatch()` sends an event to them and closes sockets that lost access (4404 after `member.removed` for that user, after `board.deleted` for everyone). `listener.py`: `Listener`, one `LISTEN` connection per process that forwards notifications to the hub. If that connection breaks (a database restart), it reconnects with `backoff_delays()` (0.5s doubling to 30s, forever) and then sends `{"type": "resync"}` to every socket through `hub.broadcast()`, because NOTIFYs sent while it was disconnected are lost. TCP keepalives catch connections that die silently. `backend_pid` is the current connection's server process; `app.state.listener` holds the listener for tests (the lifespan stops its own local one, because concurrent test clients overwrite `app.state`).
- `app/api/routes/realtime.py` — `WS /boards/{board_id}/ws`: the client's first message must be `{"type": "auth", "token": ...}` within `settings.ws_auth_timeout_seconds`; then `ready`, events, and `ping`/`pong`. It checks access with `board_role()` in a threadpool (the session is sync) and closes the session right away, so open sockets don't hold DB connections. It can't use the HTTP access aliases.
- `app/api/errors.py` — `validation_error()` and `body_validation_error()`: build the `RequestValidationError` for a rejected body or path field (for example a bad `position` or `list_id`). `check_not_frozen(card, field, value)`: the 422 for writing a comment or checklist on a frozen card.

- `.github/workflows/ci.yml` — GitHub Actions on every PR and push to `main`: a `frontend` job (`npm ci`, lint, typecheck, `format:check`, `npm test`, `build`, in `frontend/`), a `lint` job (`uv sync --locked`, `ruff check`, `ruff format --check`) and a `test` job (`pytest` against a `postgres:17` service container, database `taskboard_test`; settings come from the job's `env`). When tests fail, `.github/scripts/annotate_failures.py` turns pytest's JUnit report into one error annotation per failed test: job logs need a GitHub login, but annotations can be read through the public API (`/repos/…/check-runs/{id}/annotations`), so read those first when CI fails. `tests/test_annotate_failures.py` tests it on a real pytest run.
- `tests/` — pytest suite on PostgreSQL (`taskboard_test`, which must exist). `conftest.py` sets a test `SECRET_KEY`, rebuilds the schema from the migrations once per run (`engine` fixture), and wraps each test in a transaction that is rolled back (`db` fixture; routes' commits become savepoints, and teardown runs `SET CONSTRAINTS ALL IMMEDIATE` so every test also checks it left no duplicate positions). `TestClient`s have `get_db` overridden: `client` is logged in as alice@example.com, `anon_client` has no token, and `other_headers` is the `Authorization` header of a second user (bob) for cross-user tests. `test_migrations.py` fails if the models and migrations disagree; `committed_client` (in `conftest.py`) makes requests commit for real, with the tables truncated afterwards: `test_concurrency.py` uses it for parallel requests and `test_realtime.py` for WebSocket events (NOTIFY is only delivered on commit). `conftest.py` also points `settings.database_url` at the test database, because every `TestClient` starts the lifespan listener. WebSocket tests carry `pytest.mark.timeout(10)` so a missing event fails instead of hanging. `test_hub.py` unit-tests `BoardHub` with fake sockets, and `test_listener.py` tests reconnect and backoff with a fake connection. `test_realtime.py` fakes a database restart with `pg_terminate_backend(app.state.listener.backend_pid)`. `test_database.py` kills pooled connections the same way and checks requests still succeed.

## Reverse-engineering workflow

Four phases, each its own session, each ending with a committed file. `docs/README.md` has the same steps for readers.

1. **Observe** (roadmap step 12): Claude drives Chrome (claude-in-chrome) on Trello, one area at a time (boards, lists, cards, card details, members, …). The user logs in themselves; Claude never enters passwords. Notes go in `docs/observations/<area>.md` from `docs/observations/_template.md`: what a user can do, states, rules, edge cases, empty and error states, written as behaviour in our own words.
2. **Requirements** (step 13): turn the observations into `docs/requirements.md`. Each requirement has an ID (`R-<AREA>-<NN>`, e.g. `R-CARD-03`), a one-line user story, acceptance criteria, its source observation, and a status: `confirmed` (seen) or `unconfirmed` (inferred; check in a later observe session).
3. **Prototype** (step 14): `prototype/index.html`, one self-contained file with fake data, our own visual design, a screen for every requirement. Built from `docs/requirements.md` only. Check it by clicking through every screen in a browser; Claude also publishes it as a private artifact.
4. **Build plan** (step 15): `docs/build-plan.md` maps every requirement ID to the existing endpoints that cover it, a small API change, or a new roadmap step, then sets the order to build a real frontend.

Clean-room rules (they keep the work our own; follow them even when asked to "just take a quick look"):

- Observe sessions describe; they don't design. Design sessions (prototype, build plan) never open Trello.
- Nothing from the product goes in the repo: no screenshots, copied text, logo, name in the UI, colours or icons.
- If a design session needs something the requirements don't say, it stops and adds an open question to `docs/requirements.md` for the next observe session.

## Conventions

- Python 3.13. Annotate every function's parameters and return type.
- SQLAlchemy 2.0 style: `Mapped[...]` / `mapped_column()` in models, `select()` in queries; no legacy `session.query()`.
- Routes stay thin: validate with Pydantic schemas, return response schemas, never raw models. Put logic that more than one route needs (such as reordering cards) in `app/services/`.
- Every model change needs a migration (`alembic revision --autogenerate`), read and fixed by hand before committing: autogenerate misses things such as dropping Postgres enum types in `downgrade()`. `tests/test_migrations.py` fails until it exists.
- Positions within a parent are always 0..n-1 with no gaps among active items (archived ones have none), so ordering code uses `active_lists`/`active_cards`, never `lists`/`cards`: new items go to the end, and every move or delete goes through `app/services/ordering.py`. Validate a move before changing anything else, so a rejected request changes nothing. Routes that change positions must use an `Editable…`/`OwnedBoard` alias, so they hold the board lock.
- Every route that changes a board, its lists, cards, labels, comments or members calls `publish(..., actor_id=user.id)` after `db.flush()` (so new rows have ids) and before `db.commit()`, never after the commit. That one call also writes the activity log, so don't log separately. Delete events carry the item's name or title, so the log can still say what was deleted. Its tests in `tests/test_realtime.py` check the event. Report a rejected move as `RequestValidationError`, so its 422 has the same `detail` list shape as FastAPI's own.
- Return `404` for a missing resource and `422` for invalid input (FastAPI's default). Agreed extras: `401` for a missing/bad token or wrong login, `403` for a board member whose role is too low, `409` for a taken email or a user who is already on the board. Don't invent other codes without asking. WebSocket close codes are 4000 + the matching HTTP code: `4401` (auth), `4404` (board missing, not on it, or access lost).
- Every board, list, card and member route takes an alias from `app/api/access.py` with the lowest role it needs (`Viewable…` for reads, `Editable…` for list/card changes, `OwnedBoard` for the board itself and members). Non-members get `404`, so a board's existence stays hidden; members with too low a role get `403`. New endpoints get a cross-user test with `other_headers` and a row in the role table in `tests/test_members.py`.
- Every new endpoint gets tests in `tests/test_<resource>.py` through the `client` fixture, covering the success case and at least one error case. Write the tests first when the behaviour is clear.
- Run `uv run pytest` and `uv run ruff check .` before reporting a change as done; for frontend changes also `npm test`, `npm run lint`, `npm run typecheck` and `npm run format:check` in `frontend/`.
- Frontend: components call the API only through `src/api/`; every screen gets tests through what the user sees (labels, roles, text), with `fetch` stubbed. Use the prototype's layout and class names, never the observed product's. New dependencies are pinned to exact versions at least two weeks old (`npm install --save-exact --before=<date>`).
- Commit each reverse-engineering phase's output (observations, requirements, prototype, build plan) as soon as it exists, on its own branch and PR, like code. Long sessions get compacted and lose detail; the committed file is what the next session starts from.
- CI runs the same checks, and a PR must be green before merging. A new setting the tests need goes in the `test` job's `env` in `.github/workflows/ci.yml` too.
- The owner is learning Python: when adding code that uses a new Python or FastAPI idea (or, in `frontend/`, a TypeScript or React idea), explain the idea briefly in the reply. Code comments say why the code is the way it is (for example, why imports that look unused are needed), not teach the idea.
